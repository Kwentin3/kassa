# 1C HTML Shell Diagnostic Guide For 1C Specialist

Дата: 2026-05-19
Обновлено: 2026-05-21
Статус: Slice 2 guide draft, уточнено разделение Slice 1 / Slice 2
Назначение: инструкция для 1С-программиста по минимальному 1С Diagnostic Loader

## 1. Короткое объяснение проекта

Мы проверяем гипотезу: можно ли использовать HTML внутри 1С как современную покупательскую оболочку для кассы самообслуживания, а 1С / РМК оставить владельцем кассовой логики.

Главное правило:

```text
HTML - это экран.
1С - владелец логики и состояния.
```

HTML не должен:

- быть кассой;
- хранить настоящую корзину;
- считать финальную сумму;
- принимать решение о продаже;
- управлять оплатой;
- обращаться к ККТ;
- фискализировать чек;
- печатать чек;
- обращаться напрямую к базе 1С или оборудованию.

HTML должен только показывать состояние, принимать нажатия пользователя, отправлять намерения в 1С и перерисовывать экран по снимку состояния, который вернула 1С.

## 2. Зачем нужна диагностическая страница

У команды проекта нет собственной 1С-среды и реального кассового терминала. Поэтому сделана диагностическая web-страница:

```text
https://kassa.speechbattle.com/diagnostics/1c-html-shell
```

Ее нужно открыть внутри 1С через `Поле HTML-документа`. Страница собирает профиль среды запуска: какие HTML/CSS/JavaScript/ввод/прокрутка/визуальные возможности доступны в конкретной 1С-среде.

Результат диагностики - JSON-отчет. Его нужно скопировать или скачать и передать команде проекта.

Важно: обычный браузерный запуск полезен только как предварительная проверка. Он не доказывает, что страница так же работает внутри 1С.

## 3. Последовательность Slice 1 / Slice 2

Эти два среза не должны смешиваться:

```text
Slice 1: HTML-страница открылась внутри 1С и собрала профиль среды.
Slice 2: HTML и 1С обменялись диагностическим сообщением туда и обратно.
```

Для Slice 2 желательно уже иметь baseline-отчет Slice 1: страница открылась в `Поле HTML-документа`, сформировала JSON, а обмен HTML ↔ 1С показан как `Не подключено`. Если такой отчет уже есть, не нужно заново обсуждать возможности HTML-render: переходите к Diagnostic Loader и проверке `diag.ping`.

## 4. Входное условие: что проверяет Slice 1 без кода в 1С

Без дополнительного кода в 1С диагностическая страница уже проверяет:

- открывается ли URL;
- какой размер окна и экрана;
- какой `userAgent`;
- работают ли базовые HTML/CSS/JavaScript;
- поддерживаются ли flex/grid и другие CSS-возможности;
- работают ли SVG и простые анимации;
- работают ли нажатия, ввод, фокус и прокрутка;
- можно ли сформировать JSON;
- можно ли скопировать или скачать отчет;
- пробную загрузку CSS/JavaScript из встроенного `data:`-ресурса.

Ограничение resource-тестов: `resource.loading.css` и `resource.loading.js` в Slice 1 не загружают реальные отдельные файлы по URL. Они проверяют только встроенные `data:`-ресурсы. Это не доказывает работу путей, TLS, кэша или политики WebView для отдельных CSS/JS-файлов.

Короткий контракт по уже полученному профилю V8WebKit: [`runtime-profiles/1C_HTML_SHELL_RUNTIME_CAPABILITY_CONTRACT_V8WEBKIT.md`](runtime-profiles/1C_HTML_SHELL_RUNTIME_CAPABILITY_CONTRACT_V8WEBKIT.md). Он нужен проектной команде и будущим агентам, чтобы не закладывать в HTML-оболочку непроверенные возможности.

Без 1С Diagnostic Loader нормальное состояние отчета:

```text
Обмен HTML ↔ 1С: Не подключено
РМК-адаптер: Не проверялось
```

Это не ошибка. Это означает только то, что 1С-часть диагностического обмена еще не подключена.

## 5. Что такое Slice 2

Slice 2 - это прообраз периметрного диагностического адаптера между HTML-страницей в `Поле HTML-документа` и кодом 1С.

Он нужен не для кассы, а для одного вопроса:

```text
Может ли HTML внутри 1С отправить безопасную diag.* команду в 1С,
а 1С - вернуть ответ обратно в HTML с тем же requestId?
```

Простыми словами: HTML говорит `1С, ты меня слышишь?`, 1С принимает это сообщение и отвечает `слышу, вот тот же requestId обратно`.

Она должна:

- открыть тестовую форму 1С;
- разместить на форме `Поле HTML-документа`;
- загрузить URL диагностической страницы;
- принять тестовую команду из HTML;
- вернуть ответ обратно в HTML;
- передать в HTML безопасные сведения о среде 1С.

Минимальная успешная проверка Slice 2 - это `diag.ping` по маршруту HTML → 1С → HTML.

## 6. Что Slice 2 НЕ должен делать

Slice 2 не должен:

- добавлять товар в чек;
- получать текущий чек РМК;
- запускать оплату;
- работать с эквайрингом;
- работать с ККТ;
- фискализировать чек;
- печатать чек;
- работать с маркировкой;
- изменять кассовую сессию;
- использовать реальные товары;
- использовать реальные суммы;
- трогать боевой РМК;
- менять типовую конфигурацию без необходимости;
- использовать diagnostic loader как обход РМК.

Это только диагностический обмен HTML ↔ 1С.

## 7. Что нам нужно от вас в 5 пунктах

1. Убедиться, что Slice 1 baseline уже есть: страница открылась внутри `Поле HTML-документа` и сформировала JSON.
2. Собрать или адаптировать минимальный Diagnostic Loader в тестовой базе 1С.
3. Проверить `diag.ping`: HTML отправляет команду, 1С возвращает ответ с тем же `requestId`.
4. Передать безопасные metadata 1С: версия платформы, тип клиента, конфигурация, режим совместимости, метка терминала.
5. Вернуть итоговый JSON, журнал loader-а, скриншот и короткий комментарий, какой способ обмена сработал.

## 8. Минимальный сценарий для 1С-программиста

Исходники draft-обработки подготовлены здесь:

```text
tools/1c-diagnostic-loader/
```

Краткий handoff по source-пакету:

```text
docs/integrations/1c-html-shell/1C_DIAGNOSTIC_LOADER_README.md
```

### Шаг 1. Создать тестовую форму, обработку или расширение

Лучший первый вариант - тестовая форма во внешней обработке или расширении, чтобы не менять типовую конфигурацию без необходимости.

### Шаг 2. Добавить на форму Поле HTML-документа

На форме нужно разместить `Поле HTML-документа`. Конкретные свойства, события и доступные методы зависят от версии платформы 1С, типа клиента и режима совместимости. Их нужно проверить на целевой базе/терминале.

### Шаг 3. Загрузить URL диагностики

Откройте:

```text
https://kassa.speechbattle.com/diagnostics/1c-html-shell?runId=<уникальный_идентификатор>&terminalLabel=<метка_терминала>&verdictScope=one_c_html_field_unconnected
```

Пример:

```text
https://kassa.speechbattle.com/diagnostics/1c-html-shell?runId=test-001&terminalLabel=client-kiosk-01&verdictScope=one_c_html_field_unconnected
```

`runId` меняйте при каждой повторной проверке. `terminalLabel` - безопасная подпись терминала, без секретов и персональных данных.

### Шаг 4. Убедиться, что baseline Slice 1 есть

Проверьте, что страница открылась, прошла фазы диагностики и сформировала JSON. Если baseline уже был снят раньше, этот шаг можно не повторять.

### Шаг 5. Подключить Diagnostic Loader

Подключите код, который умеет принять только `diag.*` команду и вернуть ответ в HTML. Не подключайте РМК, оплату, ККТ или чек.

### Шаг 6. Проверить двусторонний обмен

Минимальная цель: `diag.ping` должен пройти по маршруту HTML → 1С → HTML, а `requestId` в ответе должен совпасть с входящим `requestId`.

## 9. Что такое Diagnostic Loader

Diagnostic Loader - это маленький код на стороне 1С, который работает как периметрный диагностический адаптер между HTML и 1С.

Он:

- слушает только диагностические команды страницы;
- валидирует, что команда начинается с `diag.`;
- возвращает ответ обратно в HTML;
- передает только безопасные технические metadata;
- пишет журнал обмена.

Он работает только с командами `diag.*`:

- `diag.ready`;
- `diag.ping`;
- `diag.hrefTransport`;
- `diag.domMailbox`;
- `diag.directJsCall`;
- `diag.payloadSize`;
- `diag.roundTrip`;
- `diag.getEnvironmentFrom1C`.

Эти команды диагностические. Они не являются боевыми командами кассы.

Нельзя смешивать их с будущими боевыми командами:

- `cart.addProduct`;
- `cart.addByBarcode`;
- `payment.startCard`;
- `receipt.getStatus`.

Боевой протокол будущей кассы описан отдельно в `1C_HTML_SHELL_BRIDGE_MANIFEST.md`. Slice 2 его не реализует.

## 10. Граница текущей страницы и Diagnostic Loader

Текущая диагностическая страница уже содержит объект JavaScript:

```js
window.DiagnosticHarness
```

Он может принять вызовы со стороны 1С:

- `receiveFrom1C(message)`;
- `receiveBridgeAck(message)`;
- `receiveStateFrom1C(state)`;
- `getCurrentReport()`;
- `renderReport(report)`.

Это покрывает направление 1С → HTML. Для полного Slice 2 нужно второе направление: HTML → 1С. Его можно проверить через согласованные `diag.*` hooks текущей страницы или через временные test hooks, которые добавляет Diagnostic Loader.

Если страница сама еще не отправляет `diag.ping`, это не провал Slice 2 и не доказательство, что 1С не умеет ловить события. Это означает, что нужно включить Slice 2 hooks: через текущую сборку страницы, через команду `УстановитьHTMLHooks` в draft loader-е или через временную тестовую HTML-страницу с тем же `diag.*` протоколом.

## 11. Минимальная схема обмена

```text
HTML-страница внутри Поля HTML-документа
↓
отправляет diag.ping
↓
1С принимает команду
↓
1С возвращает receiveBridgeAck(...)
↓
страница фиксирует, что обмен работает
```

Смысл `diag.ping`: проверить round-trip, а не кассовую логику.

Минимальный успешный ответ должен вернуть тот же `requestId`, который пришел из HTML.

## 12. Какие способы обмена нужно проверить

Конкретный рабочий способ зависит от версии платформы 1С, типа клиента, режима совместимости, ОС и HTML-render. Поэтому задача Slice 2 - проверить факт на целевом рабочем месте, а не спорить теоретически.

### HTML → 1С: вариант A, href/navigation transport

HTML формирует переход вида:

```text
oneshell://diag?payload=<encoded-json>
```

1С должна попытаться:

- поймать переход/нажатие/событие внутри HTML-поля;
- отменить стандартную навигацию;
- извлечь `payload`;
- декодировать JSON;
- обработать только команду `diag.*`.

Если этот способ работает, он полезен как простой транспорт HTML → 1С.

### HTML → 1С: вариант B, DOM mailbox

HTML кладет JSON-команду в скрытый элемент:

```text
#diagnostic-command-mailbox
```

и инициирует событие/нажатие на скрытый элемент:

```text
#diagnostic-command-trigger
```

1С пытается прочитать содержимое DOM-элемента и разобрать JSON.

Этот способ может быть полезен, если переход по `oneshell://` не ловится или блокируется.

### 1С → HTML: вариант A, direct JS call

1С вызывает JavaScript-функцию страницы:

```js
window.DiagnosticHarness.receiveBridgeAck(message)
```

или другой доступный в конкретной версии 1С способ вызвать функцию внутри HTML-документа.

Это предпочтительный вариант, если он стабилен.

### 1С → HTML: вариант B, DOM mailbox fallback

Если прямой вызов JavaScript не работает, 1С записывает ответ в скрытый DOM-элемент, а HTML считывает его таймером или событием.

Это fallback. Он хуже прямого вызова, но может быть достаточен для диагностического обмена, если задержка стабильна.

## 13. Формат команды из HTML в 1С

```json
{
  "diagnosticVersion": "0.1",
  "requestId": "diag-req-001",
  "command": "diag.ping",
  "payload": {},
  "timestamp": "2026-05-19T00:00:00.000Z"
}
```

Поля:

| Поле | Что значит |
|---|---|
| `diagnosticVersion` | Версия диагностического протокола. |
| `requestId` | Уникальный идентификатор запроса. Нужен для проверки ответа и повторов. |
| `command` | Имя диагностической команды. Для Slice 2 разрешены только `diag.*`. |
| `payload` | Дополнительные данные. Может быть пустым объектом `{}`. |
| `timestamp` | Время формирования команды на стороне страницы. Не использовать как источник истины. |

Правила для 1С:

- неизвестную команду не выполнять;
- команду без `requestId` считать некорректной;
- payload с секретами или кассовыми данными отклонить;
- любые ошибки возвращать как диагностический статус, а не как падение формы.

## 14. Формат ответа 1С в HTML

```json
{
  "diagnosticVersion": "0.1",
  "requestId": "diag-req-001",
  "ok": true,
  "source": "1c-diagnostic-loader",
  "payload": {
    "echo": true
  },
  "timestamp": "2026-05-19T00:00:00.000Z"
}
```

Поля:

| Поле | Что значит |
|---|---|
| `diagnosticVersion` | Версия диагностического протокола. |
| `requestId` | Должен совпадать с `requestId` входящей команды. |
| `ok` | `true`, если команда принята и обработана loader-ом. |
| `source` | Для Slice 2 ожидается `1c-diagnostic-loader`. |
| `payload` | Безопасные диагностические данные. |
| `timestamp` | Время формирования ответа на стороне 1С. |

Для `diag.ping` достаточно вернуть `echo=true` и тот же `requestId`.

## 15. Какие metadata 1С можно передать в HTML

Разрешенные безопасные данные:

```json
{
  "platformVersion": "8.3.x",
  "clientType": "thin|thick|web|unknown",
  "configurationName": "Retail|UNF|UT|custom|unknown",
  "configurationVersion": "string-or-null",
  "compatibilityMode": "string-or-null",
  "terminalLabel": "manual label"
}
```

Эти данные помогают понять, где выполнялся тест.

Если какое-то значение неизвестно, передайте `unknown` или `null`. Не пытайтесь добывать его рискованным способом.

## 16. Что нельзя передавать в HTML и JSON-отчет

Нельзя передавать:

- логины;
- пароли;
- токены;
- строки подключения;
- имена пользователей;
- персональные данные;
- товары;
- чеки;
- суммы;
- фискальные данные;
- данные карт;
- внутренние ссылки на объекты 1С;
- коммерческие данные клиента;
- содержимое cookies;
- содержимое localStorage;
- содержимое буфера обмена.

Отчет должен содержать только техническую диагностику среды и ручные наблюдения.

## 17. Что нужно вернуть команде проекта

1С-программист должен вернуть:

1. JSON-отчет со страницы.
2. Скриншот страницы диагностики, если возможно.
3. Информацию о запуске:
   - версия платформы 1С;
   - тип клиента: толстый / тонкий / web;
   - ОС терминала;
   - конфигурация: УТ / Розница / УНФ / кастом;
   - версия конфигурации, если известна;
   - режим совместимости, если известен.
4. Краткий комментарий:
   - страница открылась / не открылась;
   - были ли визуальные артефакты;
   - работали ли нажатия;
   - работала ли прокрутка;
   - удалось ли скопировать JSON;
   - удалось ли проверить `diag.ping`;
   - какой способ обмена сработал: href/navigation, DOM mailbox, direct JS call.

## 18. Минимальные критерии успеха Slice 2

Slice 2 считается успешным, если:

- страница открывается в `Поле HTML-документа`;
- 1С получает хотя бы одну диагностическую команду из HTML;
- 1С возвращает ответ обратно в HTML;
- страница меняет статус обмена HTML ↔ 1С с `Не подключено` на `Поддерживается` или `Работает частично`;
- JSON-отчет содержит результат bridge-проверки;
- в отчете видно, какой транспорт сработал.

## 19. Частичный успех

Если сработал только один транспорт - это уже полезный результат.

Примеры частичного успеха:

- href/navigation работает, DOM mailbox не работает;
- DOM mailbox работает, href/navigation не работает;
- direct JS call не работает, но DOM mailbox fallback работает;
- маленький payload проходит, большой payload не проходит;
- обмен работает в толстом клиенте, но не работает в тонком;
- обмен работает в обычном браузере, но не работает внутри 1С.

Все такие результаты нужно зафиксировать в JSON и комментарии. Это не бесполезный провал, а evidence для архитектурного решения.

## 20. Что считать провалом

Провал Slice 2:

- страница открывается, но 1С вообще не может получить событие из HTML;
- 1С получает событие, но не может прочитать payload;
- 1С получает команду, но не может ответить обратно в HTML ни одним способом;
- страница зависает или падает при попытке обмена;
- результат нельзя зафиксировать в JSON.

Даже провал полезен, если он хорошо описан: версия платформы, тип клиента, что пробовали, где именно не получилось, есть ли ошибка или просто нет события.

## 21. Для чего это все

Мы проверяем, можно ли в будущем сделать красивую покупательскую HTML-оболочку кассы самообслуживания внутри 1С.

Если обмен HTML ↔ 1С работает, то будущий интерфейс сможет:

- показывать корзину;
- принимать нажатия покупателя;
- отправлять в 1С намерение: добавить товар, удалить строку, начать оплату;
- получать от 1С новый снимок состояния;
- перерисовывать экран.

Но это будет только после отдельного этапа.

Сейчас мы не работаем с РМК. Сейчас мы проверяем только канал связи.

## 22. Предупреждение про production

Не подключать Diagnostic Loader к боевым кассовым операциям.

Нельзя:

- использовать Diagnostic Loader как обход РМК;
- давать HTML прямой доступ к базе 1С;
- давать HTML прямой доступ к оборудованию;
- использовать диагностические команды как боевые;
- вызывать кассовые процедуры из `diag.*`;
- смешивать `diag.*` с `cart.*`, `payment.*`, `receipt.*`.

Переход к РМК, чеку, оплате, ККТ и фискализации - это отдельный RMK Adapter spike.

## 23. Псевдокод / примерная логика 1С

Это псевдокод. Он показывает структуру, но не является гарантированно рабочим кодом для всех версий 1С. Его нужно адаптировать под платформу, тип клиента, форму и доступные события `Поле HTML-документа`.

```text
Процедура ПриОткрытииФормы()
    URL = "https://kassa.speechbattle.com/diagnostics/1c-html-shell"
        + "?runId=" + НовыйУникальныйИдентификатор()
        + "&terminalLabel=client-kiosk-01"
        + "&verdictScope=one_c_html_field_unconnected";

    ЗагрузитьURLДиагностикиВПолеHTMLДокумента(URL);
КонецПроцедуры

Процедура ПолеHTMLПриНажатии(Элемент, ДанныеСобытия, СтандартнаяОбработка)
    Команда = ПопытатьсяПолучитьДиагностическуюКоманду(Элемент, ДанныеСобытия);

    Если Команда <> Неопределено И НачинаетсяС(Команда.command, "diag.") Тогда
        СтандартнаяОбработка = Ложь;
        Ответ = ОбработатьДиагностическуюКоманду(Команда);
        ОтправитьОтветВHTML(Ответ);
    КонецЕсли;
КонецПроцедуры

Функция ОбработатьДиагностическуюКоманду(Команда)
    Ответ = Новый Структура;
    Ответ.Вставить("diagnosticVersion", "0.1");
    Ответ.Вставить("requestId", Команда.requestId);
    Ответ.Вставить("ok", Истина);
    Ответ.Вставить("source", "1c-diagnostic-loader");
    Ответ.Вставить("timestamp", ТекущаяДатаISO());

    Если Команда.command = "diag.ping" Тогда
        Ответ.Вставить("payload", Новый Структура("echo", Истина));
    ИначеЕсли Команда.command = "diag.getEnvironmentFrom1C" Тогда
        Ответ.Вставить("payload", ПолучитьБезопасныеMetadata1C());
    Иначе
        Ответ.Вставить("ok", Ложь);
        Ответ.Вставить("payload", Новый Структура("error", "unknown diagnostic command"));
    КонецЕсли;

    Возврат Ответ;
КонецФункции

Процедура ОтправитьОтветВHTML(Ответ)
    JSONОтвет = СериализоватьВJSON(Ответ);

    Если МожноВызватьJavaScriptНапрямую() Тогда
        ВызватьJavaScript("window.DiagnosticHarness.receiveBridgeAck", JSONОтвет);
    Иначе
        ЗаписатьОтветВДOMMailbox(JSONОтвет);
    КонецЕсли;
КонецПроцедуры
```

Практические места, которые зависят от версии 1С:

- как загрузить URL в `Поле HTML-документа`;
- как получить объект HTML-документа;
- какие события доступны: нажатие, переход по ссылке, документ сформирован;
- можно ли отменить стандартную навигацию;
- можно ли прочитать DOM-элемент;
- можно ли вызвать JavaScript-функцию;
- работает ли это одинаково в толстом, тонком и web-клиенте.

## 27. Техническое приложение

### Diagnostic command envelope

```json
{
  "diagnosticVersion": "0.1",
  "requestId": "diag-req-001",
  "command": "diag.ping",
  "payload": {},
  "timestamp": "2026-05-19T00:00:00.000Z"
}
```

### Diagnostic response envelope

```json
{
  "diagnosticVersion": "0.1",
  "requestId": "diag-req-001",
  "ok": true,
  "source": "1c-diagnostic-loader",
  "payload": {
    "echo": true
  },
  "timestamp": "2026-05-19T00:00:00.000Z"
}
```

### Список диагностических команд

| Команда | Направление | Что проверяет |
|---|---|---|
| `diag.ready` | HTML → 1С | Страница загрузилась и готова к диагностике обмена. |
| `diag.ping` | HTML → 1С → HTML | Базовый round-trip с тем же `requestId`. |
| `diag.hrefTransport` | HTML → 1С | Перехват href/navigation транспорта. |
| `diag.domMailbox` | HTML → 1С | Чтение JSON из DOM mailbox. |
| `diag.directJsCall` | 1С → HTML | Прямой вызов функции `window.DiagnosticHarness.*`. |
| `diag.payloadSize` | оба направления | Предельный размер payload. |
| `diag.roundTrip` | оба направления | Задержка round-trip. |
| `diag.getEnvironmentFrom1C` | HTML → 1С | Получение безопасных metadata 1С. |

### Разрешенные metadata

```json
{
  "platformVersion": "8.3.x",
  "clientType": "thin|thick|web|unknown",
  "configurationName": "Retail|UNF|UT|custom|unknown",
  "configurationVersion": "string-or-null",
  "compatibilityMode": "string-or-null",
  "terminalLabel": "manual label"
}
```

### Запрещенные данные

- логины, пароли, токены;
- строки подключения;
- персональные данные;
- товары, чеки, суммы;
- фискальные данные;
- данные карт;
- внутренние ссылки на объекты 1С;
- коммерческие данные клиента;
- содержимое cookies, localStorage, clipboard.

### Критерии успеха

```text
Минимальный успех: diag.ping прошел туда и обратно с тем же requestId.
Хороший результат: понятно, какие транспорты работают и какие не работают.
Нельзя считать успехом: просто открылась страница, но обмен HTML ↔ 1С не проверен.
Нельзя считать готовностью кассы: успешный diag.ping без RMK Adapter spike.
```
