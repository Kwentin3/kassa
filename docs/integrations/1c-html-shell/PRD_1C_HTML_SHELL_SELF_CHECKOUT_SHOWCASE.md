# PRD: 1C HTML Shell Self-Checkout Showcase

Дата: 2026-05-20
Статус: v0.2 refined PRD
Область: демонстрационная HTML-витрина кассы самообслуживания внутри 1С

## Executive Summary

Проектируем демонстрационную HTML-витрину кассы самообслуживания, которую можно открыть из диагностической страницы `/diagnostics/1c-html-shell` внутри `Поле HTML-документа` 1С.

Главный переход:

```text
Диагностика -> Открыть витрину -> Витрина кассы -> Назад к диагностике
```

Витрина нужна, чтобы показать клиенту UX и визуальную гипотезу современной покупательской кассы внутри HTML-render 1С. Она работает только на mock-данных и не доказывает готовность production-кассы. Реальная касса возможна только после Slice 2 Diagnostic Loader, production bridge, RMK Adapter spike и проверки чека, оплаты, ККТ, фискализации и маркировки.

Visual contract в этом PRD нужен, чтобы будущая реализация не ломала layout: карточки не вылезают за экран, корзина не растягивает страницу, важные кнопки остаются доступны, переполнение управляется только внутри явных scroll-зон.

Refine v0.2 добавляет проверяемый visual acceptance checklist, mock state machine, уточнение route/mode, edge-case mock data, безопасный edit mode fallback, anti-false-readiness banner и первый демонстрационный срез для будущего Blueprint.

## 1. Название

Рабочее название: **1C HTML Shell Self-Checkout Showcase**

Русское название: **Демонстрационная HTML-витрина кассы самообслуживания внутри 1С**

## 2. Контекст

У проекта уже есть диагностическая страница:

```text
/diagnostics/1c-html-shell
```

Она открывается внутри 1С через `Поле HTML-документа` и собирает профиль среды запуска. По фактическому Slice 1 профилю V8WebKit подготовлен runtime contract:

```text
docs/integrations/1c-html-shell/runtime-profiles/1C_HTML_SHELL_RUNTIME_CAPABILITY_CONTRACT_V8WEBKIT.md
```

Вспомогательный visual reference board:

```text
docs/integrations/1c-html-shell/SELF_CHECKOUT_SHOWCASE_VISUAL_REFERENCES.md
```

Он используется только для композиционных паттернов и анти-паттернов. Он не заменяет PRD, Blueprint и Runtime Capability Contract, не расширяет scope и не разрешает копировать чужой дизайн, бренд, иконки, цвета, тексты или hardware-specific flows.

Следующий продуктовый слой - демо-интерфейс кассы самообслуживания, который открывается из диагностики и работает в том же HTML-render. Он нужен для демонстрации клиенту, UX-обсуждения и проверки визуальной гипотезы HTML-оболочки поверх 1С.

## 3. Проблема

Нативный интерфейс 1С РМК может быть функциональным, но визуально и UX-логически слаб для покупательского сценария кассы самообслуживания.

Клиенту нужно показать:

- современный покупательский интерфейс;
- адаптивную витрину, не прибитую к одному разрешению;
- понятный поток демо-покупки;
- быструю кастомизацию;
- переключение тем;
- возможность будущей HTML-оболочки поверх 1С без переноса кассовой логики в HTML.

## 4. Цели

- Показать современную покупательскую кассу внутри HTML-render 1С.
- Дать быстрый переход из диагностики в витрину и обратно.
- Продемонстрировать адаптивную раскладку.
- Продемонстрировать темы.
- Продемонстрировать демо-режим редактирования.
- Заложить визуальный контракт карточек, сеток, корзины, текстов и переполнения.
- Показать демо-покупку на mock-данных.
- Не создавать ложного ощущения production-готовности.

## 5. Не-цели

В рамках этого PRD не делать:

- подключение РМК;
- работу с реальным чеком;
- запуск оплаты;
- работу с эквайрингом;
- работу с ККТ;
- фискализацию;
- печать чека;
- работу с маркировкой;
- production-админку;
- полноценный drag-and-drop конструктор;
- React/Vite runtime внутри HTML-поля 1С;
- CDN;
- обязательную зависимость от внешних CSS/JS;
- обязательную зависимость от системной экранной клавиатуры.

## 7. Основной сценарий

1. Пользователь открывает диагностическую страницу внутри 1С.
2. Видит кнопку **"Открыть витрину"**.
3. Нажимает кнопку.
4. Открывается демо-интерфейс кассы самообслуживания.
5. Пользователь нажимает **"Начать покупку"**.
6. Выбирает товар из каталога или поиска.
7. Товар попадает в mock-корзину.
8. Пользователь меняет количество или удаляет товар.
9. Нажимает **"Оплатить"**.
10. Видит mock-экран оплаты.
11. Видит mock-успех.
12. Может начать новую покупку.
13. Может нажать **"Назад к диагностике"**.

### 7.1. Mock State Machine

Витрина работает как простая state machine на mock-данных. Это нужно, чтобы будущий Blueprint не ушел в набор несвязанных экранов.

| State | Что видит пользователь | Основные действия | Переходы | Mock-данные | Запрещено |
|---|---|---|---|---|---|
| `idle` | Экран ожидания, бренд, промо, demo banner | Начать покупку, назад к диагностике | `shopping`, диагностика | mock-бренд, mock-промо | Запускать реальные кассовые операции |
| `shopping` | Главный экран покупки | Открыть каталог, поиск, помощь, оплатить при непустой корзине | `catalog`, `search`, `cart`, `payment_select`, `staff_required` | mock-категории, mock-корзина | Считать настоящую сумму или чек |
| `catalog` | Категории и productGrid | Выбрать категорию, добавить товар | `shopping`, `cart`, `staff_required`, `error` | mock-товары, edge-case товары | Добавлять товар в настоящий чек |
| `search` | Поиск и экранная клавиатура | Ввести текст/код, очистить, выбрать результат | `shopping`, `cart`, `error` | mock-индекс поиска, mock-товар не найден | Зависеть от OS keyboard |
| `cart` | Корзина, итог, действия со строками | Плюс/минус, удалить, оплатить | `shopping`, `payment_select`, `staff_required`, `error` | mock-корзина, mock-ошибки количества | Менять реальный чек |
| `payment_select` | Выбор mock-оплаты | Карта, СБП, отмена | `payment_processing`, `cart` | mock-методы оплаты | Запускать эквайринг |
| `payment_processing` | Демо-прогресс оплаты | Дождаться результата, отменить demo | `payment_success`, `payment_error`, `cart` | mock-timeout / mock-result | Обращаться к терминалу оплаты |
| `payment_success` | Успех и демо-чек | Новая покупка, назад к диагностике | `idle`, диагностика | mock-чек, mock-сумма | Печатать или фискализировать чек |
| `payment_error` | Ошибка mock-оплаты | Повторить, вернуться в корзину, помощь | `payment_select`, `cart`, `staff_required` | mock-код ошибки без тех. деталей | Показывать stack/JSON покупателю |
| `staff_required` | Нужен сотрудник | Позвать сотрудника, закрыть demo-сценарий | `shopping`, `cart`, `error` | mock-причина помощи | Проверять реальные права сотрудника |
| `error` | Buyer-safe ошибка | Закрыть, помощь, назад | предыдущий безопасный state, `staff_required` | mock-ошибка | Показывать внутренние ошибки |
| `edit_mode` | Overlay с зонами, рамками и demo-настройками поверх текущего state | Выбрать тему, переместить блок, сбросить раскладку, закрыть режим | Возврат в текущий state без изменения demo-покупки | mock-layout config | Сохранять production-настройки или скрывать критичные блоки |

`edit_mode` - это overlay/режим поверх текущего состояния, а не отдельная production-админка. Он не меняет mock state machine продажи и не сохраняет production-настройки.

## 8. Экраны витрины

### 8.1. Экран ожидания / приветствия

Назначение:

- бренд;
- промо;
- крупная кнопка **"Начать покупку"**;
- быстрый вход в демо;
- кнопка **"Назад к диагностике"**.

### 8.2. Главный экран покупки

Назначение:

- каталог / категории;
- корзина;
- действия;
- помощь;
- поиск;
- кнопка оплаты;
- быстрый возврат к диагностике.

### 8.3. Каталог

Назначение:

- категории;
- карточки товаров;
- добавление товара в mock-корзину.

### 8.4. Поиск

Назначение:

- поиск товара;
- собственная экранная клавиатура;
- цифровая клавиатура для ввода кода / штрихкода;
- результат поиска.

### 8.5. Корзина

Назначение:

- список товаров;
- количество;
- цена;
- сумма;
- плюс / минус;
- удалить;
- итог;
- оплатить.

### 8.6. Mock-оплата

Назначение:

- показать выбор способа оплаты;
- карта;
- СБП;
- демо-прогресс;
- успех / ошибка;
- не запускать реальный эквайринг.

### 8.7. Успех / демо-чек

Назначение:

- **"Покупка завершена"**;
- демо-номер чека;
- сумма;
- новая покупка;
- назад к диагностике.

### 8.8. Ошибка / нужен сотрудник

Назначение:

- товар не найден;
- ошибка оплаты;
- нужна помощь;
- демо-сценарий **"Позвать сотрудника"**.

### 8.9. Режим редактирования

Назначение:

- показать клиенту, что интерфейс легко кастомизируется;
- включается чекбоксом **"Режим редактирования"**;
- не является production-админкой.

### 8.10. Anti-False-Readiness Banner

На витрине должен быть ненавязчивый, но понятный служебный индикатор:

```text
Демо-режим. Данные тестовые. РМК, оплата и ККТ не подключены.
```

Он должен быть виден:

- на экране ожидания;
- в служебной панели;
- в режиме редактирования;
- в mock-оплате.

Цель - не дать клиенту или демонстратору случайно прочитать витрину как готовую production-кассу. В покупательском потоке технические термины не должны доминировать; этот banner служебный.

## 9. Адаптивная раскладка

Интерфейс не должен быть захардкожен под одно разрешение.

Профиль раскладки выбирается не по типу устройства, а по фактической рабочей области внутри HTML-render. Внутри 1С физический экран может быть `1920 x 1080`, но viewport HTML-поля может быть меньше. Все расчеты строятся от реальной рабочей области витрины, а не от физического экрана терминала.

При запуске витрина должна учитывать:

- ширину рабочей области;
- высоту рабочей области;
- соотношение сторон;
- `devicePixelRatio`;
- доступное место под шапку, основную зону, корзину и нижнюю панель.
- место под `header`, `actionBar`, `cartPanel` и `keyboardArea`;
- минимальную ширину карточки;
- минимальную высоту критичных кнопок.

Layout profiles:

| Profile | Принцип |
|---|---|
| `compact` | Меньше колонок; корзина снизу или отдельным экраном; промо минимизировано; клавиатура может занимать нижнюю зону. |
| `standard` | Каталог в основной зоне; корзина справа; нижняя панель действий. |
| `wide` | Больше колонок; расширенная корзина; промо-зона; больше воздуха. |

PRD задает принцип, а не точные пиксели. Пиксельные значения должны появиться в Blueprint после проверки на реальном HTML-render 1С.

## 10. Визуальный контракт

Цель визуального контракта - не допустить хаотичной обрезки карточек, выхода блоков за экран, наложения элементов и нечитаемых состояний.

### 10.1. Контракт рабочей области

- У интерфейса есть корневая рабочая область.
- Все содержимое должно помещаться внутри нее.
- Критичные действия не должны уходить за экран.
- Если содержимое не помещается, используется управляемая прокрутка внутри конкретной зоны.
- Горизонтальная прокрутка всей страницы запрещена как нормальный режим.

### 10.2. Контракт сетки

- Сетка строится от размера рабочей области.
- Количество колонок вычисляется по минимальной и максимальной ширине карточки.
- Gap задается design token.
- Карточки не должны становиться меньше минимального размера.
- Если карточек больше, они уходят в scroll внутри `productGrid`.
- Сетка не должна ломать корзину и нижнюю панель.

### 10.3. Контракт карточки товара

Карточка товара должна иметь:

- стабильную или управляемую высоту;
- зону изображения;
- название;
- цену;
- кнопку действия;
- опциональные бейджи.

Правила:

- изображение не должно вылезать из карточки;
- использовать `object-fit: cover` или `contain` по типу карточки;
- длинное название не должно ломать карточку;
- длинное название обрезается по строкам с визуальным многоточием или уходит в безопасную ограниченную область;
- цена всегда видна;
- кнопка **"В корзину"** всегда видна;
- карточка не перекрывает соседние карточки;
- карточка не выходит за пределы `productGrid`;
- если изображения нет, показывать аккуратный placeholder.

### 10.4. Контракт корзины

- Корзина не должна растягивать экран бесконечно.
- Список товаров прокручивается внутри корзины.
- Итог и кнопка оплаты всегда доступны.
- Длинные названия товаров не ломают строку.
- Количество и цена остаются читаемыми.
- На маленьком экране корзина может переходить в нижнюю панель или отдельный экран.

### 10.5. Контракт текстов

- Минимальный размер текста задается design token.
- Для названий товаров задается максимальное число строк.
- Длинные строки обрезаются предсказуемо.
- Не использовать слишком мелкие подписи для критичных действий.
- Критичные статусы должны быть крупными и понятными.

### 10.6. Контракт изображений

- Не требовать внешних CDN.
- Изображения должны иметь fallback.
- Отсутствие картинки не ломает карточку.
- Тяжелые изображения не использовать в первом baseline.

### 10.7. Контракт переполнения

- Никакой важный блок не должен выходить за экран.
- Переполнение допускается только внутри заранее определенных scroll-зон.
- Scroll-зоны должны быть визуально понятны.
- Критичные кнопки не должны быть внутри глубокого scroll без необходимости.

### 10.8. Контракт редактирования

- В режиме редактирования блоки можно двигать только между разрешенными зонами.
- Нельзя перетащить блок так, чтобы он перекрыл критичные действия.
- Нельзя скрыть кнопку **"Назад к диагностике"**.
- Нельзя скрыть кнопку **"Помощь"**.
- Нельзя сделать кнопку оплаты нечитаемой.
- Должна быть кнопка **"Сбросить раскладку"**.

### 10.9. Acceptance Checklist Для Визуального Контракта

Будущая реализация считается соответствующей visual contract только если проверены сценарии ниже.

Проверочные данные и состояния:

- 20 товаров;
- 50 товаров;
- 100 товаров;
- товар без изображения;
- товар с длинным названием;
- товар с очень длинным названием;
- товар с длинной ценой;
- товар с бейджем;
- товар со скидкой;
- товар **"нужен сотрудник"**;
- товар **"не найден"**;
- пустая корзина;
- корзина с 1 товаром;
- корзина с 10+ товарами;
- корзина с длинными названиями товаров;
- маленькая рабочая область;
- стандартная рабочая область;
- широкая рабочая область;
- включенный режим редактирования;
- смена темы;
- открытая экранная клавиатура;
- mock-ошибка;
- mock-успех;
- возврат к диагностике.

Ожидаемое поведение для каждого сценария:

- карточки не выходят за `productGrid`;
- карточки не перекрывают соседей;
- цена и кнопка действия видны;
- корзина не растягивает всю страницу;
- итог и кнопка оплаты доступны;
- критичные кнопки не уходят за экран;
- переполнение происходит только внутри разрешенных scroll-зон;
- горизонтальная прокрутка всей страницы не используется как нормальный режим;
- кнопка **"Назад к диагностике"** остается доступной;
- модальные окна не перекрывают служебный возврат без возможности закрытия.

## 13. Режим редактирования

Режим редактирования нужен для презентации: показать, что HTML-интерфейс легко кастомизируется. Это не production-админка.

Требования:

- чекбокс **"Режим редактирования"**;
- видимые рамки зон;
- подсветка перетаскиваемых блоков;
- возможность перемещать блоки между заранее заданными зонами;
- fallback-кнопки: вверх / вниз / влево / вправо / выбрать зону;
- перемещение блока через явный выбор зоны;
- перемещение блока выше/ниже внутри зоны;
- выбор темы;
- изменение плотности карточек;
- изменение размера карточек;
- скрыть/показать некоторые некритичные блоки;
- сброс раскладки;
- экспорт layout config в JSON как optional.

Ограничения:

- не скрывать **"Назад к диагностике"**;
- не скрывать **"Помощь"**;
- не ломать `productGrid`;
- не делать кнопку оплаты нечитаемой;
- не сохранять изменения как production-настройки без отдельного этапа.
- drag-and-drop не является единственным способом редактирования;
- **"перетаскивание куда угодно" запрещено**;
- критичные блоки нельзя скрыть;
- презентационный эффект должен сохраняться даже если drag-and-drop не сработает в V8WebKit.

## 17. Навигация диагностика ↔ витрина

Требования:

- на диагностической странице появляется кнопка **"Открыть витрину"**;
- для первого демонстрационного среза диагностика и витрина должны жить в одном совместимом single-file runtime artifact или явно связанном runtime-режиме;
- цель этого требования - снизить риск, что 1С откроет диагностику, но не откроет витрину из-за маршрутизации, кэша или загрузки второго ресурса;
- витрина сохраняет `runId` / `terminalLabel`, если они есть;
- в витрине есть кнопка **"Назад к диагностике"**;
- возврат очевиден и доступен всегда;
- кнопка **"Назад к диагностике"** не скрывается в режиме редактирования.

Допустимые варианты для будущего Blueprint:

```text
/diagnostics/1c-html-shell?mode=diagnostic
/diagnostics/1c-html-shell?mode=showcase
```

или:

```text
/diagnostics/1c-html-shell/showcase
```

PRD не выбирает окончательную техническую реализацию. Требования обязательны для обоих вариантов:

- переход диагностика -> витрина сохраняет `runId` и `terminalLabel`;
- возврат витрина -> диагностика сохраняет `runId` и `terminalLabel`;
- если используется отдельный URL, он соответствует тем же runtime-ограничениям V8WebKit;
- кнопка **"Назад к диагностике"** обязательна в showcase/diagnostic режиме.

Кнопка **"Назад к диагностике"** является служебной кнопкой showcase/diagnostic режима. Она нужна для демонстрации, тестирования и возврата к диагностике внутри 1С. Она не является частью будущего production-покупательского интерфейса.

Дополнительные правила:

- кнопка всегда видима или доступна через служебную панель;
- не скрывается в режиме редактирования;
- не перекрывается модальными окнами;
- не уходит в глубокий scroll;
- не должна быть спутана с кнопкой **"Отмена покупки"**.
