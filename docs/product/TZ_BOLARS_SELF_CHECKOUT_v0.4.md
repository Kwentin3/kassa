# ТЗ БОЛАРС Self-Checkout v0.4

## 1. Назначение

Нужно разработать интерфейс кассы самообслуживания для сенсорного терминала в цветовой теме БОЛАРС.

Основной сценарий: покупатель подходит к терминалу, сканирует товары, видит корзину, при необходимости ищет товар вручную, меняет количество, добавляет пакет, применяет скидку, может получить помощь менеджера и оплачивает покупку через эквайринг.

Интерфейс должен быть простым, крупным, понятным и рассчитанным на покупателя без специальной подготовки.

Интерфейс должен поддерживать управляемые цветовые темы и цветовые профили, чтобы оформление можно было адаптировать под бренд заказчика без переписывания экранов и логики.

Для текущего проекта базовой считается брендовая цветовая схема БОЛАРС.

Это ТЗ является upstream source of truth. PRD, visual contract, theme/tokens contract, runtime contract, screen composition spec и acceptance checklist являются downstream-документами и не должны противоречить этому документу.

## 2. Общая Структура Экранов

В MVP предполагаются следующие основные экраны:

1. Стартовый экран.
2. Экран корзины / `Ваши покупки`.
3. Экран подготовки к оплате.
4. Экран ожидания оплаты.
5. Финальный экран после успешной оплаты.

Отдельного модального окна товара с описанием товара не предусматривается.

Если товар найден через поиск или сканирование, он сразу добавляется в корзину.

Если товар уже есть в корзине, увеличивается количество существующей позиции.

Экран ошибки оплаты является состоянием payment flow. Поиск, нумпад, подтверждение отмены и таймаут неактивности являются состояниями или overlay поверх основных экранов.

## 3. Общие Элементы Рабочих Экранов

### 3.1. Шапка Рабочих Экранов

На рабочих экранах должна быть шапка.

В шапке отображаются:

1. название текущего экрана;
2. кнопка `Отменить покупку`;
3. переключатель размера текста;
4. информация о менеджере, если продажа закреплена за менеджером.

### 3.2. Кнопка `Отменить Покупку`

Кнопка находится в шапке рабочих экранов.

Название кнопки: `Отменить покупку`.

Если корзина пустая, нажатие возвращает терминал на стартовый экран.

Если корзина не пустая, при нажатии открывается модальное окно подтверждения:

`Отменить покупку и очистить корзину?`

Кнопки модального окна:

1. `Да, отменить`;
2. `Вернуться к покупке`.

При подтверждении корзина очищается, текущая покупка закрывается, терминал возвращается на стартовый экран.

### 3.3. Переключатель Размера Текста

В шапке рабочих экранов должен быть переключатель размера текста.

Нужно предусмотреть три профиля:

1. Нормально;
2. Крупно;
3. Очень крупно.

В интерфейсе это можно показать через иконку буквы в трёх вариантах `A / A+ / A++` или через три буквы разного размера.

Режим размера текста влияет на:

1. наименования товаров;
2. количество;
3. суммы по строкам;
4. итоговую сумму;
5. основные кнопки;
6. ключевые подсказки интерфейса.

Режим размера текста действует в рамках текущей покупки.

После возврата на стартовый экран режим может сбрасываться в значение по умолчанию.

### 3.4. Информация о Менеджере в Шапке

Если менеджер сканирует свою карту или служебный штрих-код, система определяет менеджера и закрепляет продажу за ним.

После успешного распознавания в шапке появляется легенда с ФИО менеджера.

Примеры:

- `Менеджер: Иванов Иван`;
- `Продажа закреплена за менеджером: Иванов Иван`.

Эта информация отображается до завершения или отмены текущей покупки.

## 4. Цветовые Темы и Цветовые Профили

### 4.1. Общий Принцип

Цвета интерфейса не должны быть жёстко зашиты в экранах.

Интерфейс должен использовать управляемую цветовую тему.

Цветовая тема должна задавать набор цветовых токенов, которые применяются ко всем экранам и состояниям интерфейса.

Это нужно, чтобы в дальнейшем можно было:

1. адаптировать интерфейс под бренд заказчика;
2. изменить палитру без переписывания логики;
3. добавить тёмную тему;
4. добавить высококонтрастную тему;
5. настроить отдельные цветовые профили для разных клиентов или торговых точек.

### 4.2. Базовая Тема MVP

Для MVP базовой темой является `БОЛАРС Светлая`.

Тема строится на узнаваемой палитре бренда БОЛАРС:

1. яркий малиново-розовый как основной брендовый акцент;
2. чёрный как логотипный и контрастный цвет;
3. белый и светло-серый как основа рабочих экранов;
4. голубой/бирюзовый как информационный и технический акцент;
5. зелёный как функциональный цвет успешного действия;
6. красный, оранжевый и жёлто-лаймовый только для специальных состояний.

### 4.3. Текущая Рабочая Цветовая Карта БОЛАРС

Текущая цветовая карта является рабочей стартовой схемой.

Если заказчик предоставит официальный брендбук БОЛАРС или точные фирменные цвета, значения цветов должны быть заменены на официальные.

| Роль | Значение |
| --- | --- |
| Primary / Bolars Magenta | `#E6007E` |
| Primary Dark Magenta | `#A9005F` |
| Logo Black | `#111111` |
| White | `#FFFFFF` |
| Light Background | `#F6F6F6` |
| Surface White | `#FFFFFF` |
| Border Gray | `#DADADA` |
| Text Primary | `#1A1A1A` |
| Text Secondary | `#666666` |
| Bolars Cyan | `#00A6C8` |
| Success Green | `#25A64A` |
| Promo Lime | `#C9E600` |
| Warning Orange | `#F5A623` |
| Error Red | `#D93025` |

Эти HEX-значения могут быть только значениями темы/профиля. Компоненты интерфейса должны обращаться к токенам, а не к конкретным HEX-значениям.

### 4.4. Рекомендуемое Применение Цветов

Primary / Bolars Magenta используется для:

1. брендовых акцентов;
2. выделения активных элементов;
3. декоративных элементов стартового экрана;
4. вторичных акцентных элементов;
5. рамок или подсветок важных блоков.

Logo Black используется для:

1. шапки;
2. контрастных панелей;
3. логотипной зоны;
4. основного текста на светлом фоне.

White используется для:

1. карточек товаров;
2. рабочих областей;
3. модальных окон;
4. нумпада;
5. списка кандидатов поиска.

Light Background используется для:

1. общего фона рабочих экранов;
2. разделения функциональных зон;
3. фона корзины;
4. фона экрана оплаты.

Bolars Cyan используется для:

1. подсказок сканирования;
2. информационных статусов;
3. зоны поиска;
4. технических подсказок;
5. статуса ожидания.

Success Green используется для:

1. кнопки `Перейти к оплате`;
2. кнопки `Оплатить`;
3. статуса успешной оплаты;
4. сообщения `Скидка применена`;
5. подтверждающих действий.

Promo Lime используется для:

1. небольших бейджей;
2. промо-меток;
3. акционных элементов;
4. вспомогательных визуальных акцентов.

Warning Orange используется для:

1. предупреждений;
2. подтверждения отмены покупки;
3. состояний, требующих внимания, но не являющихся ошибкой.

Error Red используется для:

1. ошибки оплаты;
2. нераспознанного кода;
3. товара, не найденного по штрих-коду;
4. ошибки применения скидки;
5. критичных предупреждений.

### 4.5. Цветовая Логика По Экранам

Стартовый экран:

1. допускается более активное использование фирменного малинового цвета;
2. основной текст должен быть максимально контрастным;
3. указатель сканера может использовать белый, чёрный или голубой акцент;
4. экран не должен быть перегружен.

Экран корзины:

1. основной фон светло-серый;
2. товарные строки белые карточки;
3. шапка чёрная или малиновая в зависимости от выбранного цветового профиля;
4. основные действия зелёные;
5. удаление красное только для иконки или опасного действия.

Экран подготовки к оплате:

1. фон белый или светло-серый;
2. блок итога крупный и контрастный;
3. кнопка оплаты зелёная;
4. зона скидки светлая, с голубым или малиновым акцентом;
5. пакеты отдельные карточки или кнопки с понятным выделением.

Экран ожидания оплаты:

1. фон спокойный светлый;
2. сумма очень крупная;
3. ожидание голубой информационный статус;
4. успех зелёный;
5. ошибка красная.

Финальный экран:

1. можно использовать брендовый малиновый акцент;
2. сообщение благодарности должно быть крупным;
3. экран должен автоматически вернуться на стартовый после заданного времени.

### 4.6. Управляемые Цветовые Профили

Система должна поддерживать не только одну тему, но и несколько цветовых профилей.

Минимально нужно предусмотреть:

1. `Bolars Light / БОЛАРС Светлая` - базовая тема MVP;
2. `Bolars Contrast / БОЛАРС Контрастная` - будущий профиль для повышенной читаемости;
3. `Custom / Пользовательская` - будущий профиль для ручной настройки цветов.

Для MVP можно реализовать только `БОЛАРС Светлая`, но архитектурно не закрывать возможность добавления новых профилей.

### 4.7. Цветовые Токены

Рекомендуется использовать не прямые цвета в компонентах, а токены.

Пример токенов:

1. `color.brand.primary`;
2. `color.brand.primaryDark`;
3. `color.brand.black`;
4. `color.background.default`;
5. `color.background.surface`;
6. `color.border.default`;
7. `color.text.primary`;
8. `color.text.secondary`;
9. `color.status.info`;
10. `color.status.success`;
11. `color.status.warning`;
12. `color.status.error`;
13. `color.action.primary`;
14. `color.action.secondary`;
15. `color.action.danger`;
16. `color.discount.active`;
17. `color.scanner.hint`;
18. `color.manager.badge`.

## 5. Scanner-Router

Сканер используется не только для товаров. Система должна иметь единый роутер сценариев сканирования.

При каждом считывании кода система должна определить тип кода:

1. товар;
2. скидочная карта;
3. карта / служебный штрих-код менеджера;
4. неизвестный код;
5. потенциально маркированный товар / код Честного знака.

После определения типа кода система выполняет соответствующее действие.

Если считан товар и товар найден, он добавляется в корзину. Если такой товар уже есть в корзине, количество существующей позиции увеличивается. Новая строка-дубликат для того же товара не создаётся, если по бизнес-логике товар считается тем же самым товаром.

После добавления или увеличения количества желательно визуально подсветить строку товара, чтобы покупатель понял, какая позиция изменилась.

Если считана скидочная карта, система пытается применить скидку к текущей покупке. Если скидка успешно применена, на экране отображается статус применения скидки и пересчитывается итоговая сумма.

Если считана карта менеджера, система определяет менеджера и закрепляет текущую продажу за ним. В шапке появляется ФИО менеджера.

Если код не распознан как товар, скидочная карта или менеджерская карта, система показывает понятное сообщение:

`Код не распознан. Обратитесь к сотруднику.`

Текущая корзина при этом не очищается.

### 5.1. Открытый Вопрос По Маркированным Товарам

Коллизия с маркированными товарами и Честным знаком пока остаётся открытым вопросом.

Нужно отдельно принять решение, как система должна отличать обычный штрих-код товара от кода маркировки, и какой сценарий должен запускаться при сканировании маркированной продукции.

До принятия решения этот сценарий фиксируется как нерешённый архитектурный и бизнес-вопрос.

## 6. Экран 1. Стартовый Экран

Стартовый экран показывается, когда терминал свободен и покупка ещё не начата.

На экране должна быть одна понятная инструкция без дублирования смысла.

Основной текст:

`Поднесите штрих-код товара к сканеру`

На экране должен быть визуальный указатель: стрелка или пиктограмма, показывающая, где физически находится сканер штрих-кодов.

Стартовый экран должен быть визуально спокойным и не перегруженным.

Поведение:

1. если покупатель нажимает на экран, открывается экран корзины;
2. если сканер считал штрих-код товара, открывается экран корзины, а товар сразу добавляется в корзину первой строкой.

## 7. Экран 2. Корзина / `Ваши Покупки`

Экран корзины показывает текущий состав покупки.

Он открывается в двух случаях:

1. покупатель нажал на стартовый экран;
2. сканер считал первый товар.

В шапке отображается `Ваши покупки`, кнопка `Отменить покупку`, переключатель размера текста и информация о менеджере, если менеджер уже привязан к продаже.

### 7.1. Поле Поиска Товара

На экране корзины должно быть поле поиска товара.

Поле поиска нужно для ручного добавления товара, если покупатель или сотрудник хочет найти товар без сканирования.

Поиск должен искать все вхождения по следующим данным:

1. наименование товара;
2. артикул;
3. цифры штрих-кода.

Поиск запускается после ввода `4` или более символов.

Поиск выполняется средствами 1С или runtime/search adapter, скрытым от UI за `SelfCheckoutRuntimePort`.

После ввода `4+` символов система отображает список кандидатов.

В списке кандидатов желательно показывать:

1. наименование товара;
2. артикул, если есть;
3. штрих-код или часть идентификатора, если это помогает выбрать правильный товар;
4. цену, если цена доступна на этом этапе.

Пользователь нажимает на нужного кандидата, после чего товар сразу добавляется в корзину.

Отдельная карточка товара или модальное окно с описанием товара не открывается.

Если выбранный товар уже есть в корзине, увеличивается количество существующей позиции.

### 7.2. Список Товаров

Каждая строка товара должна содержать:

1. номер позиции;
2. наименование товара;
3. количество;
4. кнопку уменьшения количества;
5. кнопку увеличения количества;
6. кнопку удаления товара;
7. сумму по строке.

В строке товара показывается именно сумма по позиции, а не только цена за единицу.

Наименование товара должно быть крупным и хорошо читаемым.

### 7.3. Изменение Количества

Количество можно менять тремя способами:

1. кнопкой `+`;
2. кнопкой `-`;
3. нажатием на само количество.

При нажатии на количество открывается экранный нумпад.

Через нумпад покупатель может вручную ввести нужное количество.

Для MVP количество считается целым числом, если отдельно не принято решение о поддержке весовых или дробных товаров.

После изменения количества пересчитываются сумма строки и итоговая сумма корзины. Пересчёт выполняет runtime/1С/backend, UI только отображает новый snapshot.

### 7.4. Удаление и Сканирование На Экране Корзины

У каждой строки товара должна быть кнопка удаления в виде иконки мусорки.

При нажатии товар удаляется из корзины.

Если покупатель на этом экране сканирует новый товар, товар добавляется в корзину.

Если товар уже есть в корзине, увеличивается количество существующей позиции.

### 7.5. Нижняя Часть Экрана

Внизу экрана отображается итог крупной строкой.

Пример: `Итого: 1 740 ₽`.

Под итогом располагается большая основная кнопка: `Перейти к оплате`.

## 8. Экран 3. Подготовка к Оплате

Экран подготовки к оплате открывается после нажатия кнопки `Перейти к оплате`.

На этом экране покупатель проверяет состав покупки, может добавить пакет и применить скидочную карту или номер телефона.

В шапке отображается `Оплата`, кнопка `Отменить покупку`, переключатель размера текста и информация о менеджере, если менеджер привязан к продаже.

### 8.1. Состав Покупки

На экране отображается краткий состав корзины:

1. товары;
2. количество;
3. суммы по позициям;
4. итоговая сумма.

### 8.2. Добавление Пакета

На экране должны быть кнопки добавления пакета:

1. Маленький пакет;
2. Средний пакет;
3. Большой пакет.

При выборе пакета он добавляется в корзину отдельной строкой.

Если такой пакет уже есть в корзине, увеличивается количество существующей позиции.

Итоговая сумма пересчитывается runtime/1С/backend и возвращается в state snapshot.

### 8.3. Применение Скидки

На экране должна быть зона для применения скидки.

Текст подсказки:

`Для применения скидки отсканируйте карту или введите номер телефона`

Сценарии:

1. покупатель сканирует скидочную карту;
2. покупатель нажимает на поле телефона;
3. открывается экранный нумпад;
4. покупатель вводит номер телефона;
5. система проверяет номер в системе лояльности;
6. система применяет скидку, если номер найден.

SMS-код на этом этапе не используется.

После применения скидки на экране нужно показать результат:

1. скидка применена;
2. сумма скидки, если она доступна;
3. итоговая сумма к оплате.

Примеры:

- `Скидка применена: -120 ₽`;
- `Итого к оплате: 1 620 ₽`.

Если скидка не найдена, система показывает понятное сообщение:

`Скидка не найдена`

Корзина при этом не очищается.

### 8.4. Привязка Менеджера

Если на этом экране менеджер сканирует свою карту или служебный штрих-код, система привязывает продажу к менеджеру.

После этого в шапке появляется ФИО менеджера.

Пример: `Менеджер: Петров Алексей`.

### 8.5. Переход к Оплате

Внизу экрана располагается основная кнопка: `Оплатить`.

После нажатия система инициирует оплату через эквайринг.

## 9. Экран 4. Ожидание Оплаты

Экран показывает состояние оплаты после отправки транзакции в эквайринг.

На экране должна отображаться итоговая сумма к оплате.

Основной текст:

`Приложите карту к терминалу оплаты`

Дополнительный статус:

`Ожидаем оплату...`

Интерфейс должен показывать результат операции:

- статус ожидания: `Ожидаем оплату...`;
- статус успешной оплаты: `Оплата прошла успешно`;
- статус ошибки оплаты: `Оплата не прошла`;
- дополнительный текст при ошибке: `Попробуйте ещё раз или обратитесь к сотруднику`.

Если оплата не прошла, корзина не очищается.

Покупателю должны быть доступны действия:

1. `Попробовать ещё раз`;
2. `Вернуться к оплате`.

## 10. Экран 5. Завершение Покупки

Финальный экран показывается после успешной оплаты.

Основной текст:

`Спасибо за покупку!`

Дополнительный текст:

`До новых встреч`

Финальный экран отображается короткое время, после чего терминал автоматически возвращается на стартовый экран.

Время показа финального экрана должно быть настраиваемым.

## 11. Таймаут Неактивности

Если на рабочих экранах нет активности, система должна закрыть текущую покупку и вернуть терминал на стартовый экран.

Таймаут неактивности должен быть настраиваемым параметром.

Значение по умолчанию можно принять как `5 минут`.

Активностью считаются:

1. касание экрана;
2. сканирование товара;
3. ввод в поле поиска;
4. выбор кандидата из поиска;
5. изменение количества;
6. удаление товара;
7. ввод телефона;
8. сканирование скидочной карты;
9. сканирование карты менеджера;
10. переход между экранами;
11. добавление пакета.

Если операция оплаты уже отправлена в эквайринг и система ожидает ответ от платёжного устройства, автоматический сброс по таймауту не должен ломать процесс оплаты.

## 12. Управляемые Элементы Интерфейса и Workflow

Чтобы не захардкодить полезные настройки, нужно отдельно предусмотреть управляемость следующих элементов.

6. время показа финального экрана;
7. состав кнопок пакетов;
8. названия пакетов;

## 13. Основной Пользовательский Сценарий

1. Покупатель подходит к терминалу.
2. Видит стартовый экран с подсказкой поднести штрих-код товара к сканеру.
3. Сканирует товар.
4. Открывается экран `Ваши покупки`.
5. Первый товар добавляется в корзину.
6. Покупатель сканирует остальные товары.
7. При необходимости покупатель ищет товар вручную через поле поиска.
8. Поиск запускается после ввода `4+` символов.
9. Покупатель выбирает товар из списка кандидатов.
10. Выбранный товар добавляется в корзину.
11. При необходимости покупатель меняет количество через `+`, `-` или нумпад.
12. При необходимости покупатель удаляет товар из корзины.
13. Покупатель нажимает `Перейти к оплате`.
14. На экране оплаты проверяет состав покупки.
15. При необходимости добавляет пакет.
16. При необходимости применяет скидочную карту или вводит номер телефона.
17. Если покупателю помог менеджер, менеджер сканирует свою карту, и продажа закрепляется за ним.
18. В шапке появляется ФИО менеджера.
19. Покупатель нажимает `Оплатить`.
20. Система отправляет транзакцию в эквайринг.
21. Покупатель прикладывает карту к платёжному терминалу.
22. Система показывает статус оплаты.
23. После успешной оплаты показывается экран благодарности.
24. Терминал возвращается на стартовый экран.

## 14. Системные Состояния

В интерфейсе нужно предусмотреть следующие состояния:

1. терминал свободен;
2. покупка начата;
3. корзина пустая;
4. товар добавлен;
5. товар уже был в корзине, количество увеличено;
6. товар удалён;
7. количество изменено;
8. поиск товара выполняется;
9. кандидаты поиска найдены;
10. кандидаты поиска не найдены;
11. товар не найден по штрих-коду;
12. скидка применена;
13. скидка не найдена;
14. менеджер привязан к продаже;
15. ожидание оплаты;
16. оплата успешна;
17. оплата не прошла;
18. покупка отменена;
19. сработал таймаут неактивности;
20. код не распознан;
21. маркированный товар / Честный знак: сценарий требует отдельного решения;
22. активная тема загружена;
23. тема не загружена или загружена с ошибкой;
24. используется цветовой профиль по умолчанию.

## 15. Открытые Вопросы

### 15.1. Маркированные Товары и Честный Знак

Необходимо отдельно определить, как терминал должен работать с маркированными товарами.

Открытые вопросы:

1. как отличать код маркировки от обычного штрих-кода товара;
2. должен ли покупатель сканировать только товарный штрих-код или код маркировки тоже;
3. что делать, если маркированный товар требует дополнительной проверки;
4. кто отвечает за сценарий ошибки по маркировке;
5. как этот сценарий связан с 1С, кассой, фискализацией и оборудованием.

До принятия решения сценарий маркированных товаров не считается финализированным.

### 15.2. Официальный Брендбук БОЛАРС

Текущая цветовая карта является рабочей.

Желательно запросить у заказчика или бренда БОЛАРС официальный брендбук, логотипы и точные фирменные цвета.

Если официальный брендбук будет предоставлен, цветовую карту нужно привести к официальным значениям.

## 16. Ключевые Требования к UX

Интерфейс должен быть рассчитан на сенсорный экран.

Основные кнопки должны быть крупными.

Тексты должны быть хорошо читаемыми.

Наименования товаров должны быть особенно заметными.

Цветовая схема должна помогать покупателю ориентироваться, а не перегружать экран.

Брендовые цвета БОЛАРС нужно использовать как узнаваемый визуальный слой, но рабочие экраны должны оставаться чистыми, контрастными и удобными.

Покупатель должен всегда понимать:

1. что он уже добавил;
2. сколько товаров в корзине;
3. какая сумма к оплате;
4. применена ли скидка;
5. закреплена ли продажа за менеджером;
6. что делать дальше.

Каждый экран должен ясно вести покупателя к следующему действию.

## 17. Runtime Boundary

Frontend не должен напрямую дёргать backend, 1С, эквайринг, scanner-router, search service, loyalty system или theme source из разных компонентов.

Нужна одна логическая точка общения frontend с внешним миром: `SelfCheckoutRuntimePort` или аналогичный runtime/bridge/facade contract.

Frontend отправляет пользовательские намерения через typed commands, а получает авторитетный state snapshot.

UI-компоненты не должны сами решать бизнес-логику.

В прототипе MVP внешние контуры могут быть воспроизведены через `MockAdapter`, но это не отменяет продуктовую границу с 1С, системой лояльности, scanner-router и эквайрингом.
